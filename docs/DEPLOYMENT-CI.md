# النشر الآلي والتحقق من الإنتاج

سير العمل `.github/workflows/deploy.yml` هو المسار الرسمي لنشر `main` والتحقق من الموقع الحيّ. لا يحتاج أي وصول إلى لوحة Railway من خارج GitHub، ولا يطبع أي سر في السجلات.

## ماذا يفعل سير العمل

| الوظيفة | متى تعمل | ماذا تفعل |
|---|---|---|
| **فحوص الجودة والبناء** | كل دفع إلى `main`، **وكل طلب دمج** (يتجاهل تغييرات `*.md` و`docs/**` و`verification/**` في الدفع فقط) | `pnpm typecheck` ثم `format:check` ثم `test` (يلزم FFmpeg) ثم `pnpm build` بنفس أمر الحاوية |
| **النشر على Railway** | بعد نجاح الفحوص، عند الدفع أو التشغيل اليدوي فقط | ينشر عبر Railway CLI **فقط** إذا وُجد `RAILWAY_TOKEN`؛ بلا رمز يُتخطّى ويُترك النشر لتكامل GitHub |
| **التحقق من الإنتاج** | بعد الجودة عند الدفع/التشغيل اليدوي | ينتظر حتى يصبح الإصدار المنشور هو نفس التزام `main`، ثم ينفّذ عقد الفحوص على `PRODUCTION_URL` |

المجموعة `production-deploy` تمنع نشريْن متوازيَيْن، بينما طلبات الدمج تُشغّل فحوص الجودة في مجموعة منفصلة فلا تصطف خلف نشر إنتاجي طويل. وظيفتا النشر والتحقق لا تعملان من طلبات الدمج. الفشل في أي فحص يجعل التشغيل أحمر ويمنع اعتبار النشرة سليمة.

**سببان لفصل النشر عن التحقق:** تكامل GitHub في Railway قد ينشر تلقائيًا من `main`، فيكون أمر CLI تكرارًا غير ضار؛ ولأن تقييدات الشبكة أو صيغ أوامر CLI تتغير، يبقى **التحقق هو الحكم** لا مجرد نجاح أمر النشر.

> **قاعدة إصدار pnpm:** لا تُضِف input باسم `version` إلى `pnpm/action-setup`، لأن `packageManager` في `package.json` يحدد `pnpm@10.28.2` أصلًا، ووجود الاثنين يُسقط الوظيفة برسالة `Multiple versions of pnpm specified`. ترك الإدخال فارغًا يجعل الإجراء يقرأ النسخة ويمحو بصمة التجزئة `+sha512…` بنفسه. ولهذا يعمل سير العمل الآن على **طلبات الدمج** أيضًا: تعديلات CI نفسها تُختبر قبل الدمج لا بعده.

## إعداد GitHub (مرة واحدة)

Settings → Secrets and variables → Actions.

**Variables** (غير سرية):

| الاسم | القيمة | مطلوب |
|---|---|---|
| `PRODUCTION_URL` | `https://yemreact-production.up.railway.app` | لا — لكن يُنصح بضبطه لتغيير النطاق دون تعديل الملفات |

**Secrets** (سرية):

| الاسم | من أين | مطلوب |
|---|---|---|
| `RAILWAY_TOKEN` | Railway → المشروع → **Settings → Tokens → New Token** ببيئة `production` | اختياري: بدونه لا ينشر CLI، ويُتوقّع أن ينشر تكامل GitHub |
| `RAILWAY_PROJECT_ID` | `383b7d01-6af9-4305-978c-7cc92ac6335b` | مع الرمز |
| `RAILWAY_ENVIRONMENT_ID` | معرّف بيئة `production` | مع الرمز |
| `RAILWAY_SERVICE` | اسم الخدمة، فقط إن كان المشروع بأكثر من خدمة | عند الحاجة |

> **أمان:** أي رمز مشروع في Railway يمنح حامله قراءة **كل متغيرات بيئة المشروع** (أسرار الدخول الاجتماعي ومفاتيح الجلسة). لا تلصقه في محادثة أو ملف في المستودع أو سجل تشغيل. أنشئه ببيئة واحدة، ودوّره فورًا إن انكشف، واحذفه عند عدم الحاجة.

## إعداد خدمة Railway

| المتغير | القيمة | الأثر عند إغفاله |
|---|---|---|
| `NEXT_PUBLIC_SITE_URL` | `https://yemreact-production.up.railway.app` | يُدمج **وقت البناء**؛ بدونه تبقى روابط OG و`sitemap.xml` وJSON-LD على `localhost:3000` (يفشل فحص `sitemap-origin`) |
| `DATA_DIR` | `/app/data` مع **Volume مثبّت على `/app/data`** | تُفقد قاعدة SQLite والملفات المرفوعة عند كل إعادة نشر |
| `OAUTH_SITE_URL` | نفس النطاق العام، HTTPS إلزامي | يُبنى منه `redirect_uri`؛ وبلا مزوّد مهيّأ لا يوجد دخول أصلًا |
| `OAUTH_<PROVIDER>_CLIENT_ID` / `_SECRET` | من Google/Apple/Microsoft | الدخول الاجتماعي معطّل |
| `FFPROBE_PATH` | `/usr/bin/ffprobe` (مضبوط في Dockerfile) | يُبحث عنه في PATH |

روابط العودة المسجّلة عند كل مزوّد: `https://yemreact-production.up.railway.app/api/auth/oauth/<provider>/callback`.

تذكير: **نسخة واحدة فقط** من الخدمة، لأن قاعدة البيانات SQLite محلية على القرص. ورقّي حساب المالك من طرفية الخدمة:

```bash
ADMIN_USER_ID='<معرف الحساب>' pnpm admin:create
```

## قراءة النتائج

- **ملخص التشغيل**: صفحة التشغيل في GitHub ← وظيفة «التحقق من الإنتاج» ← `Summary`، وفيه جدول كل فحص ونتيجته.
- **التقرير الخام**: أثر (Artifact) باسم `production-verification` يحوي `verification/deployment/result.json`.
- **النقطة الحيّة**: `GET /api/health` تُرجع مستوى الإعداد (`ok` / `warn` / `fail`) وفحوصًا مفصّلة **دون أي سر أو بيانات حساب أو أسماء ملفات**: عدد الرياكشنات، عدد حسابات المالك، العنوان العام، المسار الثابت، وهل المزوّدون مهيّأون. تُستخدم أيضًا كسطر إنذار مبكر عند تغيّر الإعداد.

## التشغيل اليدوي ومحليًا

```bash
# من صفحة Actions: Run workflow، أو تحقق من المنشور دون نشر
node scripts/verify-deployment.mjs https://yemreact-production.up.railway.app

# فحص أي نسخة محلية أو معاينة
node scripts/verify-deployment.mjs http://localhost:3000

# انتظار وصول التزام محدد قبل الفحص (كما تفعل الوظيفة الآلية)
node scripts/verify-deployment.mjs "$URL" --expect-revision "$(git rev-parse HEAD)" --wait 900 --poll 15
```

الخيارات: `--wait` مدة الانتظار بالثواني (افتراضياً 900)، `--poll` دور إعادة الفحص (15)، `--json` مسار تقرير JSON، `--request-timeout` مهلة كل طلب بالمللي ثانية. الأمر يعيد **1** عند فشل أي فحص و**0** عند نجاحها جميعًا.

## ما يتحقق منه العقد

إحالة `/` إلى `/library` · صفحة المكتبة عربية RTL كHTML · **وصول الإصدار الجديد إلى الإنتاج** · عقد `/api/health` وبلا فحص فاشل · `/api/reactions` بلا تخزين مؤقت (مسار الفحص الصحي في `railway.json`) · تطابق `sitemap.xml` و`robots.txt` مع النطاق العام · ترويسات `nosniff` و`Referrer-Policy` و`Permissions-Policy` · صفحة التفاصيل 200 والرمز المجهول 404 · تسليم الوسائط مع دعم `Range` (206) للملفات المرفوعة · الصفحات العامة `/collections` و`/saved` و`/help` و`/privacy` و`/login`.

**خارج نطاق هذا العقد**: الدخول الاجتماعي الحقيقي (يحتاج متصفحًا وجلسة)، رفع الملفات، قياسات Lighthouse، وأي كتابة على البيانات. هذه تبقى فحوصًا يدوية موصوفة في [تقرير الجودة](QUALITY-REPORT.md).

## تشخيص الأعطال

| الأثر | السبب المرجّح | الحل |
|---|---|---|
| `انتهت مهلة الانتظار … الخدمة لا تُبلّغ عن إصدار` | Railway لم تنشئ نشرة من الالتزام، أو `RAILWAY_GIT_COMMIT_SHA` غير متاح في الخدمة | تأكد من تكامل GitHub مع الفرع `main`، أو أضف `RAILWAY_TOKEN` لينشر CLI، أو شغّل «تحقق فقط» لفحص المنشور الحالي |
| `النشرة الحالية لا تتضمن /api/health بعد` | الإصدار المنشور أقدم من هذا التغيير | انشر الإصدار الجديد أولًا |
| `sitemap … بدل https://…` | `NEXT_PUBLIC_SITE_URL` غير مضبوط أو أُضيف بعد البناء | اضبطه في متغيرات خدمة Railway ثم **أعد البناء** |
| `فحوص فاشلة: uploads` | القرص الدائم غير مثبّت أو بصلاحيات خاطئة | ثبّت Volume على `/app/data`؛ المدخل يصلح الملكية تلقائيًا |
| `فحوص فاشلة: ffprobe` | FFmpeg غير مثبّت في صورة النشر | Dockerfile يثبّته؛ تأكد من استخدام `Dockerfile` كباني |
| `فحوص فاشلة: site-url` | النطاق العام `http` أو `localhost` (يحدث أيضًا عند تشغيل بناء إنتاج محليًا بلا ضبط المتغير) | استخدم نطاق HTTPS العام؛ ولبناء محلي شغّل `pnpm dev` أو اضبط المتغير قبل `pnpm build` |
| `Failed to fetch … from Google Fonts` أثناء البناء | `next/font/google` في `src/app/layout.tsx` يجلب الخطوط الأربعة **وقت البناء** | بيئات البناء تحتاج `fonts.googleapis.com`؛ إن كانت محجوبة اسمح بها أو انقل الخطوط لاستضافة ذاتية (`next/font/local`) |
| تحذيرات فقط (`warn`) | إعداد ناقص غير مُعطِّل: لا مزوّد دخول، لا حساب مالك، `DATA_DIR` نسبي | أكمل الإعداد؛ التحذير لا يُسقط التشغيل |

## أدلة محلية

عقد الفحوص مُختبر على نسخة محلية عاملة (منفذ 3000): 10/10 ناجحة، وعند تمرير نطاق لا يطابق `NEXT_PUBLIC_SITE_URL` يفشل فحصَا `sitemap-origin` و`robots-origin` بكود خروج 1 كما هو مقصود، وعند طلب إصدار لا يصل تفشل وظيفة الانتظار برسالة إجرائية.
